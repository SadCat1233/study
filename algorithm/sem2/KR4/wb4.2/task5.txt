Задание 5

Способ 1. Хеш-таблица и счетчики оценок

Основная идея:
хранить соответствие "идентификатор студента -> оценка" в хеш-таблице.
Дополнительно хранить массив счетчиков для оценок 2, 3, 4 и 5.

Структура данных:
- hash table: id студента -> оценка;
- count[6], где count[2], count[3], count[4], count[5] хранят количество
  студентов с соответствующей оценкой.

Обработка запросов:

1. Найти оценку студента по id:
   обращаемся к хеш-таблице по ключу id.

   Средняя сложность: O(1).
   Худшая сложность: O(N), если возникло много коллизий, но на практике при
   хорошей хеш-функции запрос выполняется почти за O(1).

2. Определить количество студентов с заданной оценкой:
   обращаемся к массиву count по индексу оценки.
   Сложность: O(1).

Память:
- нужно хранить все идентификаторы студентов;
- для каждой записи хранится оценка;
- есть дополнительные накладные расходы хеш-таблицы;
- массив счетчиков занимает O(1) памяти.

Итоговая память: O(N), но с достаточно большими накладными расходами.

Плюсы:
- очень быстрый поиск оценки по id;
- очень быстрый подсчет студентов с заданной оценкой;
- хорошо подходит для большого количества запросов.

Минусы:
- хеш-таблица требует больше памяти, чем простой массив;
- при 10 миллионах записей накладные расходы могут быть заметными.


Способ 2. Отсортированный массив записей и счетчики оценок

Основная идея:
хранить записи в массиве, отсортированном по идентификатору студента.
Для быстрого подсчета оценок отдельно хранить счетчики оценок.

Структура данных:
- sorted array: пары (id студента, оценка), отсортированные по id;
- count[6] для количества студентов с оценками 2, 3, 4 и 5.

Обработка запросов:

1. Найти оценку студента по id:
   выполняем бинарный поиск по отсортированному массиву.

   Сложность: O(log N).

2. Определить количество студентов с заданной оценкой:
   обращаемся к массиву count.

   Сложность: O(1).

Память:
- хранятся только сами записи;
- нет больших накладных расходов хеш-таблицы;
- массив счетчиков занимает O(1) памяти.

Итоговая память: O(N), но обычно меньше, чем у хеш-таблицы.

Плюсы:
- экономнее по памяти;
- данные можно хранить компактно;
- поиск остается достаточно быстрым даже при 10 миллионах записей.

Минусы:
- поиск по id медленнее, чем в хеш-таблице;
- при частом добавлении новых записей нужно поддерживать сортировку.


Trade-off между скоростью и памятью

1. Хеш-таблица + счетчики:
   - максимальная скорость;
   - оба типа запросов выполняются за O(1) в среднем;
   - требуется больше памяти из-за накладных расходов хеш-таблицы.

2. Отсортированный массив + счетчики:
   - меньше памяти;
   - запрос количества студентов с оценкой выполняется за O(1);
   - поиск оценки по id выполняется за O(log N).

3. Обычный массив:
   - меньше всего дополнительных структур;
   - оба запроса выполняются за O(N);
   - для 10 миллионов записей и частых запросов не подходит.


Оптимальный выбор

Оптимальным решением будет использовать хеш-таблицу для поиска оценки
по идентификатору студента и массив счетчиков для количества студентов
с каждой оценкой.

Причины:
- запрос оценки конкретного студента выполняется за O(1) в среднем;
- запрос количества студентов с заданной оценкой выполняется за O(1);
- оценки принимают только 4 возможных значения, поэтому счетчики занимают
  константно мало памяти;
- система рассчитана на частые запросы, поэтому скорость важнее небольшого
  увеличения памяти.

Если ограничение памяти очень жесткое, можно выбрать второй способ:
отсортированный массив записей и счетчики. Тогда поиск по id будет O(log N),
но потребление памяти будет ниже.


Ответ

Для быстрого решения задачи нужно хранить:
1. Хеш-таблицу:
   id студента -> оценка.
2. Массив счетчиков:
   count[2], count[3], count[4], count[5].

Сложность запросов:
- найти оценку по id: O(1) в среднем;
- найти количество студентов с заданной оценкой: O(1).

Память:
- O(N) для хранения записей;
- O(1) для счетчиков оценок.

Вывод:
лучшее решение по скорости - хеш-таблица вместе со счетчиками оценок.
Если память важнее скорости, можно использовать отсортированный массив
и бинарный поиск.
